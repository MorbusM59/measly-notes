# Thockdown Notes — canonical docs

This project's documentation is kept deliberately small. These are the load-bearing documents; nothing else in the repo should be treated as authoritative project doctrine.

## Git workflow
Non-local (remote/cloud) sessions: once a change is committed and pushed to its working branch, merge it straight into `main` yourself (a fast-forward, when the branch is a clean descendant of `main`) rather than opening a pull request and waiting on review. Push `main` directly. Skip this and fall back to a normal branch+PR (or ask first) when the merge isn't a clean fast-forward, or when the user asks for a PR instead. Local sessions are unaffected — this default is for non-local sessions only.

## Releases
One command: `npm run release` (patch bump), or `-- minor` / `-- major` / `-- 0.7.2`. It gates on a clean, in-sync `main` and a passing test suite, pauses for you to write the release notes, tags and pushes, builds Windows locally, waits for the macOS DMG on GitHub Actions, then uploads and checksum-verifies every asset before leaving it staged as a prerelease. Re-running the same command resumes an interrupted release rather than starting over. See [docs/release-protocol.md](docs/release-protocol.md) — read that before touching `scripts/release.mjs` or `.github/workflows/build-mac.yml`.

## Read first
- [docs/guiding-vision.md](docs/guiding-vision.md) — the product's spiritual guideline: why this app exists and who it's for. Written for the AI agent, not for end users; let it inform judgment calls, don't surface it to users.
- [docs/engineering-doctrine.md](docs/engineering-doctrine.md) — **how work is done here, and the standing division of labour**: the human moves fast and loose, the agent is the deliberate counterweight answerable for the codebase's coherence. **Vet before building** — when an idea arrives, state the concerns before writing code, and let it be refined until it can be built cleanly; an idea implemented faithfully but incoherently is a failure, not a delivery. The rules it carries, each anchored to a real incident:
  1. **Find the bone, never splint the limb.** Ask whether this is where the fault IS or where it SHOWS.
  2. **When pieces will not fit, step up a level.** A change that needs a special case to coexist is being made at the wrong level.
  3. **Never converge by retrying.** Wait until the information is there, then hit the target by design. No loop-until-timeout, no try-look-try-again.
  4. **A rule stated once must hold everywhere it applies.** This codebase's characteristic failure is correct reasoning applied to one caller and not its sibling.
  5. **Understand the system before measuring it.** Questions about the CODE (what does this do, why, what calls it, does its original reasoning still hold) are answered by READING — the answer is already written down. Only questions about the WORLD (how long, does it drop frames, what did the browser actually do) are answered by MEASURING. Reaching for a measurement on a code question is the characteristic error: it is slow and it produces confident false positives that send a fix one layer above the fault. Before running anything, state the question, what would refute the hypothesis, and why this instrument can discriminate — including what it cannot see.
  6. **Test the property, not the step.** A walk, drift or oscillation needs an iterating test that asserts the fixed point.
  7. **Delete what the fix makes dead, in the same change** — tests, constants, plumbing, and the docs that describe it.
  8. **No workarounds, ever.** Pre-alpha: there is no user to shield and no release to protect.
  9. **A document that describes the code is part of the code.** Mark a superseded section superseded; a stale description is believed.

  It also carries **the order of work**, which is front-loaded onto understanding on purpose: read the docs → analyse the code → understand the components AND their interactions → understand why things are the way they are → check whether that reasoning still holds → draft a plan in which the idea places cleanly → **discuss the plan before building, naming what could not be determined by reading** → measure only what reading cannot answer → execute with a sanity check at each step → hand over for user testing. **When a check contradicts the plan, stop and return to the analysis — never fix forward.**

## Architecture contracts
- [docs/editor-contract.md](docs/editor-contract.md) — the boundary between app features and the editor internals (CM6Editor.tsx is the sole `EditorAdapter` implementation as of the Lexical fallback's removal — see `docs/cm6-parity-hardening-plan.md`).
- [docs/interaction-design-philosophy.md](docs/interaction-design-philosophy.md) — rules for input, caret, scroll, and note-activation behavior.
- [docs/adventure-platform.md](docs/adventure-platform.md) — how the adventure game is BUILT: a director that owns a stack of stages, the persisted save, the effect vocabulary (stages never write — they return effects and the director applies them), and the three rules the types enforce so a game can be left at any screen and resumed on it. The platform contains no rules; the game itself (Thockquest) is content. Read it before touching anything under `src/adventure/`, and keep its open-questions list current — it is the handover between sessions on this feature, and it names every deliberate placeholder. **Do not fill those in.**
- [src/escapeMenu/escapeMenuContract.ts](src/escapeMenu/escapeMenuContract.ts) — how a feature *lives inside* the escape-hold quick-actions ring instead of merely being launched from it: cells contributed to the ordinary ring, and a mode that replaces the ring wholesale while it is up (cells, prompt, running-state line, and whether activating a cell closes the menu). `EscapeHoldPanel.tsx` owns geometry, rotation, focus and close behaviour regardless; a mode never reimplements the dial. Every input that turns the dial — arrow keys, `Tab`, and the mouse wheel over the ring (one notch = one arrow press, via `editor/wheelNotch.ts`'s shared notch resolver) — goes through one `rotateOneStep`, so no input can drift apart from the others. A mode may also carry `status` — a title, a headline and readouts the HOST renders on the two bars around the editor. That split is deliberate and load-bearing: the ring's centre label names the cell you are about to activate and nothing else, so a mode never narrates through the dial. **Which bar takes which is also a rule** (`EscapeMenuStatus.tsx`): STATE goes UP to the tab bar, where a reader looks for what they are holding; NARRATION goes DOWN to the chapter bar, where they look for what is going on. The adventure game (`src/adventure/`) is the first and currently only consumer — the ring itself knows nothing about it. It is reached by RIGHT-CLICKING the User Guide window control (which then lights and shows a flame), and it takes over an editor slot the way the guide does — see **slot overlays** below — except that it EMPTIES the slot so the game plays over a blank editor. A mode may also declare `onDismiss`, which is what makes lowering the ring end the game rather than leave an occupied slot with nothing in it: the ring IS the game's interface, so it cannot outlive it. The converse is the same observation from the other side and is enforced for every consumer: **a note arriving in a slot lowers the ring** — in a note the text is the content and the ring is a menu over it, so a ring left up over a note the reader just chose is a menu they did not ask for. Everything below that hinge is pure and content-driven (see `docs/adventure-platform.md`); the save persists as `PersistedMenuState.adventure` through both halves of the state-persistence contract below.
- [src/shared/slotOverlay.ts](src/shared/slotOverlay.ts) — **what a slot is showing when it is not showing a note** (the User Guide, the adventure, an undocked note), and the invariant the whole mechanism exists to enforce: *stored state may never contradict the screen; where they disagree the screen wins, by construction of `occupancyOf` rather than by a correction*. There is ONE record, and it is return memory, not a claim about what is displayed. The guide is not recorded for display at all — showing the guide IS having one of its notes active, so every route in (the window control, a `$HELP` link, a restored session, a link from another note) reads correctly with no code of its own. The adventure and an undocked note do read the record, but always corroborated against the slot, so a stale record is inert rather than wrong. Sections REPORT their occupancy to `App.tsx`, which aggregates; nothing watches a section in order to retract a flag. Read this before touching the window control, the slot views, or anything that activates a note.
- **State persistence** has two independent, equally load-bearing halves — a bug in either one silently reverts a setting on restart, and each has actually shipped that way at least once:
  - *Renderer side* (`src/App.tsx`): any immediate (non-debounced) write to the persisted app-state menu MUST go through `persistMenuStateNow` — never hand-roll `buildMenuStateSnapshot` + `saveAppState` directly, and never call `persistMenuStateNow` itself from a handler declared earlier in the file without going through `persistMenuStateNowRef` (TDZ forbids depending on it directly; a plain dependency array silently pins the call to a stale, pre-persistence-ready closure instead — see that ref's own doc comment for how this was found live). Hand-rolling the direct pattern, or triggering two independent immediate persists in the same synchronous handler (see `persistMenuStateOnce`'s `extraOverrides` param), silently reverted settings on restart — confirmed as the actual cause at least five separate times across double-size mode, sidebar visibility, the options-menu auto-show-sidebar path, and review-gutter visibility.
  - *Main-process side* (`electron/stateService.ts`): every field on `PersistedMenuState` (`src/shared/appState.ts`) needs a matching line in `sanitizeMenu` — it's a hand-maintained allowlist both `saveAppState` and `loadAppState` route every payload through, and a field missing from it is silently dropped on every real read/write, no matter how correct the renderer-side code is. `isDoubleSizeMode` shipped an entire release this way. **The browser-mode mock (`src/dev/installBrowserMockBridges.ts`) does not catch this class of bug** — it clones state verbatim and never calls `sanitizeMenu` at all, so a fix verified only against `dev:browser` can look completely correct and still be broken in the real app. (The mock now seeds a stand-in User Guide family — the same fixed ids, sealed and timeless, one chapter, placeholder prose — plus one ordinary note, so guide behaviour can be exercised there at all. It is the SHAPE only: anything that reads the guide's real text still needs the real app.) Verify persistence changes against `electron/stateService.ts` directly (see `electron/stateService.test.ts` for the pattern: a temp-dir `StateService`, a *fresh second instance* reading back what the first wrote, simulating a real restart — not the same instance's own cache) or a real Electron build, not just the browser mock.

  If you're adding a new instant menu-state toggle or a new persisted field, both halves are required, not optional groundwork to skip.

## Diagnostic traces (opt-in, cost nothing when off)
These `localStorage` flags turn on traces built for defects that only reproduce in a real session. Each attaches nothing when unset; set the flag, reproduce, read, unset.
- `thockdown:debug-cage-state` — one line per keypress from the edit view's caret-cage reconcile: where the caret sat, what CM6 moved on its own (its height-map revision compensation), the height change, the target, what was written, and scroll/height/text rows separately. **Text movement is scroll movement minus height change** — reading the scroll number alone will mislead you, and did for most of a session. Also buffered on `window.__cageTrace` (last 400), because a console filter or another flag's flood will otherwise hide the one line you need: `copy(window.__cageTrace.join('\n'))`.
- `thockdown:debug-preview-window` — **the whole windowed-scroll story in one buffer** (`editor/scrollTrace.ts`): the block window (`win`), the travel engine (`journey`), and the long-journey curtain (`bridge`). They share a buffer because they are three views of one event — a travel plans a journey, the journey clamps against whatever the mounted window can hold, the window re-anchors under the curtain, and the curtain covers the moment it does. A defect in one presents as a symptom of the others, so separate buffers would mean reordering the halves by eye, which is exactly the reconstruction that hides ordering bugs. Every line carries `scrollTop` where it has one, because a movement of the WINDOW and a movement of the READER look identical from outside and are not the same event.
  - `win` (`usePreviewWindow.tsx`) — each adjustment pass with its geometry, each window move (marked `FRONT` when the leading edge moved, the only kind that has to compensate scroll), each carry of the reader across such a move, each landing, and the two branches that used to be silent: `defer` (a journey owns the scroller, so the window will not move for that journey's whole duration — the first thing to suspect when a travel across a large note stalls) and `hold` (the pass ran and declined to move, with the `headroom` the mounted window can still absorb; headroom near 0 plus a hold is the reader against a boundary the window is refusing to open).
  - `journey` (`NonQuantizedSmoothScroll.ts`) — the plan, with `asked` against `reachable`, which differ precisely when the destination is not in the scroller's space; every `PINNED` frame where the engine asked for a position the scroller could not give, counted rather than logged per frame (one is rounding, forty is a wall — this is what "the scroll did not arrive" looks like from the inside); the `CUT` and what `onBridgeCut` handed back; and the landing, marked `SHORT` when the target was outside the scroller.
  - `bridge` (`scrollBridge.ts`) — why `begin` declined, when it does (no host box, no style, no tile), and the arithmetic that decides whether the curtain can read as text at all: pixels per frame, **viewports per frame**, and **tiles per frame**. More than a viewport per frame and the reader sees disjoint slices rather than motion; near a half-multiple of the tile period those slices alternate between two phases and it reads as a flicker rather than as text — the wagon-wheel case `BRIDGE_TILE_LINES` was chosen to avoid, which the trace names in words when it detects it. Also flags a curtain that was raised and never advanced.
  - The flag is read **live**, not latched at first use, so it can be switched on from the console with the symptom still on screen — these defects are intermittent and a reload loses them. Buffered on `window.__previewWindowTrace` (last 400): `copy(window.__previewWindowTrace.join('\n'))`.
- `thockdown:debug-wheel` (`editor/wheelTrace.ts`, written by `CM6Editor.tsx`'s `handleWheel` and the render view's in `usePreviewScrollbar.ts` — one shared buffer, because a gesture can cross panes; the render view's lines all start `preview`) — one line per wheel event in the edit view: the raw `deltaY`/`deltaMode`, the learned notch size and pixel remainder (`editor/wheelNotch.ts`), `scrollTop` before/after/one-frame-later, and the **top visible line number** before and after, plus every silent decline. Start here for any "scrolling feels wrong" report: the first question is what the device is actually sending, and a wheel that moves `scrollTop` without moving the text is indistinguishable from one that does until the line number is on the line. Buffered on `window.__wheelTrace` (last 400). The render view's lines cover the same ground for spin-to-keep-scrolling there: every nudge with the pixels it is worth, every swallowed spin tail, and why each coast ended.
- `thockdown:debug-preview-settle` (`src/editorSection/previewSettleTrace.ts`) — why the render view was revealed after a note load, and what moved afterwards. A visible settle in render view does NOT by itself mean the settle gate is too short: it means either that the gate revealed at a real fixed point and something moved AFTER it, or that it gave up on its safety bound/timer, or that it never engaged at all. Those are indistinguishable from outside and need different fixes, so every reveal names its own reason. The post-reveal watcher then follows the geometry for 2.5s and reports **`scrollTop`, `scrollHeight` and the block container's height separately, plus `textShift`** — the on-screen position of one latched block, which is the only number that says what the READER saw: a `scrollHeight` jump with `textShift` at 0 is the scrollbar thumb alone, while a non-zero `textShift` is the reflow being reported. (Same lesson as the cage trace's: text movement is scroll movement minus height change.) A latched block merely UNMOUNTING is not counted as movement — counting it reported a phantom reflow on a capture where all three geometry numbers were flat at zero delta, which is the opposite of what the watcher is for. Buffered on `window.__previewSettleTrace` (last 400): `copy(window.__previewSettleTrace.join('\n'))`.
- `thockdown:debug-frame-cost` (`src/editorSection/previewFrameCostTrace.ts`) — what scrolling the render view costs, per frame: one line per scroll run carrying `frames`, `median`, `p95`, `max` and a dropped-frame count. Start here for any "scrolling feels wrong" report, because it answers in the units the complaint is made in. Reported as a distribution and never as a mean, deliberately: scrolling that is smooth except for a hitch every twenty frames reads as broken, and a mean erases exactly that — the p95 and the dropped count are what a reader feels, the median only says whether the baseline is healthy. Runs under ten frames are discarded as nudges, and scrolls fired while the settle gate is holding are ignored (those are the restore's, not the reader's). **Useless in the Claude Code browser pane**, which never composites and never fires rAF, so it has to be read in the real app. Buffered on `window.__previewFrameCostTrace` (last 200). Built to settle whether the continuous pane could stop virtualizing — it could, and it has — and kept because "is scrolling slow now" keeps coming back.
- `thockdown:debug-focus` (`src/dev/focusDiagnostics.ts`) — every mousedown in the capture phase with `defaultPrevented`, what holds focus one frame and one tick later, and every focusin/focusout naming both parties and their section column.
- `thockdown:debug-input-lag` — the pre-existing keystroke/scroll-sync trace. Loud; turn it OFF before reading either of the others.

## Verification rigor: match the size of the change
Two tiers, chosen by judgment, not by rote:
- **Substantial/structural work** (new features, architecture or contract changes, cross-cutting refactors, anything touching editor/scroll/performance-critical code): gold standard. Live-browser Playwright verification (not just code reading), the full existing regression-script suite, `npm test`, `tsc`/`lint`, and an A/B check (e.g. `git stash`) proving a fix's own test actually fails without it. Update the relevant living doc/JSDoc history.
- **Small, well-understood fixes and extensions** (isolated bug fixes, cosmetic tweaks, small additions with an obvious blast radius): light pipeline. Reproduce the issue, apply the minimal fix, verify the fix actually resolves it (a targeted live check beats guessing from code), done. Don't run the full regression suite or unit test suite out of habit — that cost is disproportionate to a small, isolated change and burns session budget for no added confidence.
When unsure which tier applies, ask rather than defaulting to the expensive path.

### Diagnosing a live defect (learned the hard way, repeatedly)
Order of operations, cheapest and most decisive first:
1. **Get the state difference, not the theory.** When the same code path works sometimes, the fastest question to the user is "what is the minimal difference between a run that works and one that doesn't". "Works if I reload on X, fails if I reload on Y" localizes a bug faster than any amount of code reading, and only the user can produce it.
2. **Diff the two runs.** With a working path and a failing path in hand, log both and compare. If the logs are identical through the suspect code (they were here), the fault is in runtime state or ordering, not in the branch you were about to rewrite.
3. **Take one runtime measurement that splits the hypothesis space.** Here, three numbers -- the computed target, what the scroller could hold, and where it actually ended -- killed "miscomputed" and "clamped" in a single read and left only "discarded". That is worth more than another speculative patch.
4. **Instrument decision points, including the silent ones.** Log what was computed, which branch ran, and what each early return declined to do. Every unlogged `return` in a correction path is a place the bug can hide.
5. **Only then change code.**

**Know what your instrument cannot do.** `dev:browser` in the Claude Code Browser pane does not composite, so `requestAnimationFrame` never fires there: anything rAF-scheduled (the settle gate, the anchor-jump correction, every retry loop in the editor) simply does not run, and measurements of it are meaningless rather than merely imprecise. Establish whether the path under test can even execute in the instrument *before* trusting a result from it -- and never ship a speculative fix to timing-sensitive code that the instrument cannot exercise. Shipping unverified guesses to the user's running app burns their time and can break working behavior; it did both here.

**Smoke-load after touching hook-level code.** `tsc` does not catch temporal-dead-zone ordering (a `const` ref declared after the callback that closes over it), and the symptom is a blank app, not a type error. Load the app once before handing it back.

## Docs hygiene
Point-in-time planning/migration records (phase trackers, decision ledgers, validation matrices) are not kept once their work ships — the shipped code and the docs above are the source of truth. Don't recreate that pattern; if a doc is a snapshot of a finished effort, fold anything non-obvious into the relevant living doc or TODO.md and delete it rather than archiving it.
